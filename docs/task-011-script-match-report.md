## 1. 分段策略（B 类自主决定）

### 1.1 规则

| 级别 | 规则 |
|---|---|
| 一级 | **作者写的句子**：句末标点 `。！？!?；;…` 与换行。**`max_chars` 以内原样保留，再短也不合并** |
| 二级 | 句子超过 `max_chars` → 按句内标点 `，,、：:` 再切 |
| 三级 | 仍超过 → 硬切（**兜底**，不是首选） |
| 收尾 | **只有我们自己切出来的碎片**才按 `min_chars` 并入邻片 |

默认 `max_chars=32`、`min_chars=6`，都可配置（`match_max_chars` / `match_min_chars`）。

### 1.2 理由

**为什么上限是 32 字**：中文 CLIP 文本塔 `context_length = 52`，去掉 `[CLS]`/`[SEP]`
只剩 **50 token**。汉字多数 1 token，但生僻字会拆成多个 —— 32 字留足余量，
避免**静默截断**（截断不会报错，只会让匹配悄悄变差）。

**为什么按句切而不是按固定字数切**：依据是 **TASK-009 的实测教训** —— 当时向量由整段
`answer` + 标签算出，**长回答稀释了标签的区分度**，检索 top-1 只有 2/10。
文案同理：一段里塞三个意思，一个向量表达不了。句末标点是作者给的语义边界，比字数更准。

**为什么"作者写的短句不合并"**（这一条是实测改出来的）：
第一版我把所有短于 `min_chars` 的片段都合并，测试立刻抓到问题 ——
`夜幕降临。` 只有 5 个字，但它是一个**完整的句子、作者的一个节拍**，不该被并掉。
真正该并的是**我们自己切出来的碎片**（`然后，` 这种 2 字残片）。
所以合并只作用于二级/三级切分的产物。

**`max_chars` 是软目标**：合并碎片会让个别片段略微超过它。真正的硬约束是 50 token，
32 字留了足够余量 —— 宁可略超，也不要留下没有画面语义的碎片。

### 1.3 分段实测

```
输入：「夜幕降临，深色的天幕上散布着点点星光。屏幕上显示出绚丽的彩色分形图案，
       不断向中心延伸。整个画面是纯黑的，看不到任何内容。…」（9 句）
输出：9 段，与句末标点一一对应
```

## 4. 唯一不对的那段：根因分析（如实报告）

```
「整个画面是纯黑的，看不到任何内容。」
  期望 black（纯黑，无任何内容）
  top-1 = mptestsrc（黑底 + 白色点阵方格），相似度最高
  正确项 black 的真实名次: 15 / 16   ← Top-5 里根本没有
  完整排名: [mptestsrc, colorspectrum, green, gradients, blue, cellauto, life,
            red, testsrc, noise, smptebars, rgbtestsrc, testsrc2, mandelbrot,
            black, white]
```

### 两个根因（都是实测出来的，不是猜的）

**根因一：纯色画面在 CLIP 空间里几乎不可分。**

实测单色镜头之间的余弦相似度：

|  | gradients | black | white | red | blue | colorspectrum |
|---|---|---|---|---|---|---|
| **black** | 0.8159 | 1.0000 | **0.9990** | 0.8196 | 0.8949 | 0.7297 |
| **white** | 0.8093 | **0.9990** | 1.0000 | 0.8118 | 0.8877 | 0.7243 |

**纯黑与纯白的余弦是 0.9990** —— 在 CLIP 眼里几乎是同一个向量。
这不是实现问题：CLIP 是在**自然照片**上训练的，**纯色块属于它的训练分布之外**。

**根因二：「看不到任何内容」这种否定式描述，CLIP 表达不了。**

`mptestsrc` 的关键帧平均亮度 **7.6/255**（实测），肉眼几乎就是黑的，
但它左上角有一块白色点阵 —— 于是它比"真·纯黑"更贴文案。
CLIP 无法理解"**没有内容**"是一个语义要求。

### 这对 V1 意味着什么

- **不算实现缺陷**：匹配逻辑与 TASK-010 完全一致（§5 有逐字段一致性测试）
- **是模型能力边界**：这类"纯色 / 无内容 / 否定式"描述在当前模型上不可靠
- **人的兜底仍然有效**：`match_select` 允许直接指定任意镜头（§6 有演示），
  所以人不会被卡住 —— 只是**这一段的 Top-N 推荐没帮上忙**

**我没有为了让验收 2 通过而调大 N**（N=15 才够，那等于把全库都推荐给你，失去推荐的意义）。

## 6. 人工调整演示（验收 3）

工具：`match_show`（查看）/ `match_select`（替换/指定）/ `match_reorder`（调序）。

**实测输出**（第 0 段）：

```
当前候选:
  0. shot#13 colorspectrum  score=0.5037
  1. shot#3  life           score=0.5009
  2. shot#9  blue           score=0.4880
  3. shot#4  gradients      score=0.4858
  4. shot#5  cellauto       score=0.4800

$ match_reorder --segment_index 0 --shot_id 9 --direction up
  → [13, 9, 3, 4, 5]        # shot#9 上移到第 2 位

$ match_select --segment_index 0 --shot_id 13
  → selected_shot_id = 13   # 选中的镜头被显式记录
```

**存盘与重读**：结果写在插件数据目录 `matches/<名字>.json`。
测试 `test_adjustments_survive_a_reload_of_the_plugin_context` 会**关掉上下文、
重新装配插件、再读**，断言选中项与顺序都还在。

**手动指定库外候选**：`match_select` 传一个不在候选里的镜头 → 从素材库取信息，
插到候选**首位**并标 `manual: true`、`score: null`。

> 为什么手动插入的候选**不给分数**：分数是"检索排名"的产物，人指定它不是检索的结果。
> 硬塞一个 cosine 进去会让"分数"这个词在同一个列表里有两个含义。

### 为什么用 JSON 而不是塞进素材库的 SQLite

匹配结果是**人工调整过的编辑决策**，不是从素材算出来的派生物。它有独立生命周期
（可改名、可复制、可 diff、可给人看），也不该被 `library_rebuild` 清掉。
库是"素材的派生数据"，匹配结果是"人的产物"。

## 8. B 类自主决定清单

| # | 决定 | 取值 | 理由 |
|---|---|---|---|
| 1 | **分段粒度** | 句末标点一级；上限 **32 字**；下限 **6 字** | 32 字 = 中文 CLIP 50 token 限制留余量；句末标点是作者给的语义边界（TASK-009 长文本稀释语义的教训） |
| 2 | **短片段合并范围** | **只合并我们自己切出的碎片**，不合并作者写的短句 | 第一版全合并，被测试抓到 `夜幕降临。` 被误并；作者的节拍不该动 |
| 3 | **Top-N 默认值** | **3** | 验收下限是"每段至少 3 个"；再多会稀释"帮你选好了几个"的体验 —— 人在少数几个里挑，不是翻长列表 |
| 4 | **结果存储格式** | 插件数据目录下 `matches/<名字>.json` | 人工编辑的产物，独立生命周期；不该被 `library_rebuild` 清掉 |
| 5 | **工具划分** | `script_match` / `match_show` / `match_select` / `match_reorder`（4 个） | 对应任务书列的三件事（查看 / 替换 / 调序）+ 入口。**"替换"与"手动指定"合成一个 `match_select`** —— 都是"这段用哪个镜头"，分成两个工具会让人猜该用哪个 |
| 6 | **手动候选是否给分数** | **不给**（`score: null` + `manual: true`） | 分数是检索排名的产物；塞 cosine 会让"分数"一词在同一列表里有两个含义 |
| 7 | **工具风险等级** | 全部 `read` | 只读写插件自己的数据目录，不碰素材库、不碰源视频 |
| 8 | **匹配耗时优化** | 准备阶段只做一次，打分循环复用 | 不是"为将来预留"，是消除一次调用内的**明显重复 I/O** |
| 9 | **语料** | 新建 16 画面（一画面一视频） | TASK-009 的 7 种图案语义区分度不足以检验文案匹配；一画面一视频可排除镜头切分的干扰 |

---

## 9. 局限

1. **语料是合成图案，不是真实素材。** 8/9 这个数字**不能外推到真实视频** ——
   真实素材有自然纹理、人物、场景，CLIP 在那些内容上才是"在分布内"的。
   合成纯色块恰恰是 CLIP 最弱的地方（§4 有实测）。**下一个任务应当在真实素材上重测。**
2. **抽象文案匹配无效**：B 组实测三个候选分数挤在 0.46–0.49，名次由噪声决定。
   V1 没有"这条文案在库里没有对应内容"的识别与提示。
3. **评测规模小**：9 段文案、16 个镜头。没有统计显著性可言。
4. **ground truth 由我人工判定**，且**我第一版还标错了两处**（§3.2）。
   没有第二个人复核。
5. **分段没有做语义级切分**：只按标点与长度。一段里跨两个主题的情况没处理。
6. **`shot_id` 在强制重分析后会变**（TASK-009 遗留性质）——
   匹配结果保存的是 `shot_id`，**强制重分析后这份结果会指向错的镜头**。
   本次记录，未修。
