## 任务边界：禁止"顺手"

### 规则

**任务书没写的事，不在本次任务中做。**

发现"顺手能改进的地方"时，**写进报告的《发现但未做》一节，不在本次任务中执行**。

### 唯一的例外

不改就**通不过本任务验收标准**的东西 —— 例如实现过程中撞出来的、直接挡住验收的缺陷。

这种必须同时满足两条，缺一不可：

1. 在报告里**单列**，并写明**它对应哪一条验收标准**；
2. 明确写清"**为什么它是范围内**"，而不是"顺手"。

**除了这一种，一律走《发现但未做》。**

> 犹豫的时候不做。判断"它算不算范围内"所花的时间，
> 远小于一次越界改动出错的恢复时间。

### 为什么

- **不是所有"改进"都是安全的** —— 越界的改动既不被本次验收标准覆盖，也不被本次测试覆盖
- **超出范围的改动没有经过验收检查** —— 本次任务的验收标准管不到它，
  等于"改了一个没人验的东西"
- **一次"顺手"出错，可能要花十倍时间恢复**

### 反面教材（本项目真实发生，2026-10-05）

TASK-017 是"改扫描器的 5 个方向"，任务书写得很清楚：**纯数据改动**。

我顺手多做了一件事：把 `TASKS.md` 的变更记录按时间重排。
脚本用**截断的条目名**去匹配，重建表格时**丢掉了 4 条记录**。
从备份恢复 + 逐条核对所花的时间，**远多于重排本身带来的收益**。

而重排这件事：**任务书没要求、没验收标准、没人验、出了问题也没人会发现**
（如果不是我当场核对行数）。

**这条规则就是从这个错误来的。**

### 报告要求

**每份交付报告都要有《发现但未做》一节**，没有就写"无"。

这一节至少写清三件事：

| 项 | 说明 |
|---|---|
| 发现了什么 | 具体到文件 / 函数 / 行为 |
| 为什么觉得该改 | 依据（实测数据、缺陷复现、规范冲突） |
| 为什么这次不做 | 它不在哪条任务书范围内 |

**"发现了但没写下来" = 没发现。** 写下来是为了让它进下一轮排期，
而不是默认它会被忘掉。

## AI 能力隔离

### 原始规则

> 插件禁止直接调用模型 SDK；模型调用必须经过 Core 的 AI 能力层（`ctx.ai.*`）。

### 细化（TASK-010 架构裁决，2026-10-05）

TASK-010 引入"插件提供本地模型 Provider"之后，"直接调用模型 SDK"这句话出现了歧义：
**实现一个 Provider 必然要 import 它运行模型所需的东西**。据此细化为：

#### 1. 插件**业务代码**禁止

- import 任何**远端模型 SDK**：`openai` / `ollama` / `anthropic` / `litellm` 等
- import 任何 **HTTP 客户端**：`requests` / `httpx` / `aiohttp` / `urllib` / `http.client` 等
- 直接发起**远端模型调用**

判据是"**是否绕过能力层去够远端模型**"，不是"有没有出现某个词"。

#### 2. 插件提供的 **Provider 实现**允许

- import **本地推理运行时**（`onnxruntime` 等）
- **但业务代码不得直接调用该 Provider** —— 必须通过 `ctx.ai.*` 走 Core Capability

也就是说：**Provider 文件是"模型实现"，业务文件是"模型使用者"**，
两者在同一个插件目录里可以共存，但职责不能混。

#### 3. 禁词表

| 类别 | 处理 |
|---|---|
| 远端 SDK / HTTP | **保留在禁词表**，照旧 0 命中 |
| 本地推理运行时 | **不在禁词表里**；改为约束"**仅限 Provider 文件使用**" |

**实测核对（无需改代码）**：项目现有的禁词表**本来就不含本地推理运行时** ——

```python
# tests/test_ai_capability.py
FORBIDDEN_IN_PLUGINS = [
    "openai", "ollama", "anthropic", "litellm",
    "requests", "httpx", "aiohttp", "urllib", "http.client",
]
```

它针对的就是"远端 SDK / HTTP"。所以第 3 条的"从禁词表移除"**在现有表上已经是成立的**，
不需要动任何代码。

### 判定与证据（TASK-010 §7）

| 文件 | 性质 | 对禁词表 | 结论 |
|---|---|---|---|
| `plugins/video_analyzer/plugin.py` | **业务代码** | **0 命中** | ✅ 只用 `ctx.ai.embed_images()` / `ctx.ai.provider()` |
| `plugins/video_analyzer/xbc_va_clip.py` | **Provider 实现** | 不在禁词表内 | ✅ `import onnxruntime` 属于本类允许项 |

端到端证据：中文 CLIP 的图片向量**只经** `ctx.ai.embed_images()` 产出，
文本向量**只经** `ctx.ai.embedding()` / `ctx.ai.provider()` 产出；
业务代码里没有一处 import 推理运行时，也没有一处直接调用 Provider 实例的方法
（除了经 `ctx.ai.provider(...)` 取回对象后调用其能力方法 —— 那正是能力层路由的结果）。

完整判定与理由见
[《TASK-010 交付报告》](task-010-retrieval-quality-report.md) §6。

### 与既有表述的关系

磁盘上原本只有两处相近表述，都在代码注释里（本次**未改动代码**）：

| 位置 | 原文 |
|---|---|
| `src/xbc/core/capabilities/ai/__init__.py` | 插件通过 `ctx.ai` 使用；**业务插件不得直接调用模型** |
| `src/xbc/core/capabilities/ai/provider.py` | 插件只依赖 `AIService`，**永远不直接依赖 Provider** |

两者与本节一致：**"业务插件"是约束对象，"Provider"是允许的例外**。
本节把"业务代码 / Provider 实现"的边界写明，让这条规则可执行而不是靠语义猜测。

### 尚未机械化的部分（待裁决）

"**本地推理运行时仅限 Provider 文件使用**"这条**目前只写在文档里，没有测试守着**。
若要机械 enforce，需要一个新检查（例如：扫描 `plugins/` 下每个 `.py`，

## 每日 GitHub 扫描（广度兜底）

### 定位：与"任务前调研"并列，不互相替代

| | 触发 | 作用 | 粒度 |
|---|---|---|---|
| **任务前调研** | 任务书下来时 | 为**这个任务**找候选、做选型 | 点 |
| **每日扫描** | 每天定时 | 没有任务书时也保持**领域广度** | 面 |

**两条规则必须同时成立：**

1. **扫描结果 ≠ 任务前调研已完成** —— 每日简报只是"可能值得看"的线索，
   真要用某个项目，仍要走《常驻规则：调研结果的使用》的六项登记（许可证、可商用、
   使用方式、架构冲突、封装位置），许可证必须读原文。
2. **任务前调研也不能只靠扫描** —— 扫描只覆盖本节这五个方向的关键词，
   任务书点名的技术（例如某个具体模型）要专门查。

### 扫描范围：**只扫这五个方向，无关领域不扫**

| # | 方向 | 覆盖什么 |
|---|---|---|
| 1 | **视频处理** | 镜头切分 / 视频结构 / 视频理解 / 多模态 |
| 2 | **素材管理** | 素材库、标签、检索、向量索引、媒体资产组织 |
| 3 | **AI 能力层** | 本地模型（Ollama 生态）、模型路由、能力层抽象 |
| 4 | **声音克隆** | TTS、音色克隆、配音 |
| 5 | **文案匹配** | 文案 / 脚本与画面或素材的匹配、内容自动化（**收窄到"文案"**，不再泛扫营销） |

**明确不扫**：插件内核机制、桌面宿主框架、账号/授权/插件商城/更新分发、
以及任何与上面五项无关的领域。**相关性不够就不出现在报告里**，
不要为了"看起来扫了很多"把无关项堆进报告。

### 输出收敛：有就写，没有就一行

| 扫描结果 | 输出 |
|---|---|
| **有实质候选** | 写简报：项目是什么、与我们的关系、建议动作（引入依赖 / 仅参考 / 忽略）、许可证风险 |
| **无实质候选** | **一行"今日无"**，不展开、不凑数、不罗列全部命中项 |

**"实质候选"的判据**（三条都满足才算）：

1. 落在上面五个方向里；
2. **有可能改变我们的某个决定** —— 引入某个依赖、替换某个实现、放弃某个方案；
3. 现在就能说清"拿它干什么"。

只是"相关"、只是"star 多"、只是"看起来不错"—— **都不算**。

### 定论机制：定论必须附「重新评估触发条件」

台账里写的结论分两档，**用词不许混**：

| 档位 | 写法 | 要求 |
|---|---|---|
| **定论** | "结论：X 方案不需要换" | **必须同时写出「重新评估触发条件」** —— 什么事件发生时这条要重开 |
| **当前判断** | "当前判断：……（尚未定论）" | 可以说，但不许用"不需要""已经确定"这类措辞 |

**触发条件必须是可观察的事件**，不能是"以后再看看""有需要时再说"。例：

- ✅ "当出现**内核零依赖**之外的新约束（例如允许引入 OpenCV 级依赖）时重开"
- ✅ "当**同一个问题被第二次提出**时重开"
- ❌ "以后有更好的方案再说"

**没有触发条件的结论，一律降级成"当前判断"。**

### 判断留痕：判断过就落盘

每日扫描里**判断过**的项目（无论结论是引入、参考还是忽略），
都要记进 [docs/research/README.md](research/README.md) 的「每日扫描判断记录」表——
否则同一个项目明天会被"重新发现"一次，浪费判断。

**只报告不落盘的判断，等于没判断。**
