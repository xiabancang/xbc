## 0. 为什么会有这份报告

TASK-009 做出了两个核心技术选型，但**当时没有做调研**，理由只写在交付报告里：

1. **用 SQLite 存素材库**，不用向量数据库
2. **语义检索用全表扫描 + Python 余弦**，不用 ANN 索引

TASK-009 任务书的「输出」只要求交付报告，**没有要求调研报告** —— 所以这不是漏交。
但按《调研结果的使用规则》，涉及第三方方案的选型应当有登记。**本报告补上这一环。**

同时，补做调研的过程**推翻了交付报告里的一处估算**（见 §2），该估算已更正。

## 1. 候选方案登记表

按规则补齐六栏（许可证 / 可商用 / 使用方式 / 架构冲突 / 时效性）：

| 方案 | 语言 | 许可证 | 可商业使用 | 使用方式 | 架构冲突 | 时效性 |
|---|---|---|---|---|---|---|
| **当前实现：全表扫描 + Python 余弦** | Python | 不适用（自写） | — | **从零** | 无 | — |
| [sqlite-vec](https://github.com/asg017/sqlite-vec) | C | **Apache-2.0** | ✅ | **从零**（本次不采用） | **有**：需加载 C 扩展（`.dll`），与"单文件插件"冲突 | 2026-05-18（近 5 个月无提交） |
| [hnswlib](https://github.com/nmslib/hnswlib) | C++ | **Apache-2.0** | ✅ | **从零** | **有**：header-only C++，pip 安装需编译工具链 | 2026-09-15 活跃 |
| [faiss](https://github.com/facebookresearch/faiss) | C++ | **MIT** | ✅ | **从零** | **有**：重量级，带 BLAS 依赖，包体积大 | 2026-10-03 活跃 |
| [chromadb](https://github.com/chroma-core/chroma) | Rust | **Apache-2.0** | ✅ | **从零** | **有，且是原则性的**（见 §1.2） | 2026-10-04 活跃 |
| [USearch](https://github.com/unum-cloud/USearch) | C++ | **Apache-2.0** | ✅ | **从零** | **有**：需要 C++ 轮子 | 2026-10-02 活跃 |
| [annoy](https://github.com/spotify/annoy) | C++ | **Apache-2.0** | ✅ | **从零** | **有**：需构建；且维护放缓 | **2025-10-29（近一年无提交）** |

**许可证结论：六个候选全部允许商业使用**（Apache-2.0 × 5、MIT × 1）。
`APACHE-2.0` 与 `MIT` 都无 copyleft 传染 —— **许可证不是这次不采用的理由**。

> 每个许可证均经 GitHub API `license.spdx_id` 确认，不是从 README 推断。
> 维护状态取 `pushed_at`。

### 1.1 为什么不采用：架构冲突（不是许可证）

夏半仓的硬约束是「**内核零第三方依赖**」+「**插件尽量零依赖、单目录即完整插件**」。
上面每一个候选都要往插件里塞一个**编译产物**：

| 方案 | 塞进来的东西 | 后果 |
|---|---|---|
| sqlite-vec | 平台相关的 `.dll`（需 `enable_load_extension`） | 插件不再是"纯 Python 单目录"；Windows 下要分发二进制 |
| hnswlib / USearch / annoy | C++ 扩展轮子 | 同上有二进制；annoy 还要构建 |
| faiss | 大体积 C++ 库 + BLAS | 插件体积与依赖数量都失控 |
| chromadb | 完整向量数据库引擎 | 远超"存 14 个镜头的向量"的需求 |

**当前实现是 0 字节依赖、纯标准库** —— 这是拿性能换来的，而 TASK-009 的语料**不需要那个性能**（14 个镜头，2.6ms）。

### 1.2 chromadb 的原则性冲突（单独说明）

chromadb **自带 embedding function**（会在内部直接调用嵌入模型）。

这与夏半仓的硬约束「**插件通过 Core Capability 调 AI，不直接调模型**」**方向相反** ——
引入它等于在素材库里开了一条绕过 `ctx.ai` 的模型调用路径。
一旦某次入库走了它的 embedding function，向量就不再来自 `ctx.ai`，
`provider` / `model` 的记录会失真，**TASK-007 的"跨 Provider 向量不可比较"约束也就失效了**。

**这是"不用"的充分理由，不需要再看性能。**

> 与 `docs/research/README.md` 里 `ollama-python` 的判定同一条道理：
> **凡是把"调模型"封装成插件可以直接 import 的库，都与能力层隔离冲突。**

## 2. 实测：当前实现的真实成本（更正交付报告的估算）

交付报告初版给的是**估算**（"1,000 镜头约 10–50ms、10,000 镜头约 0.1–0.5s"）。
实测下来**低估了 4–22 倍**：

| 镜头数 | 向量体积 | 解码（ms） | 余弦计算（ms） | **合计（ms）** | 交付报告初版估算 |
|---|---|---|---|---|---|
| 14（本次语料） | 42 KB | 0.3 | 2.3 | **2.6** | "无感" ✔ |
| 100 | 300 KB | 2.1 | 17.3 | **19.4** | — |
| 1,000 | 3 MB | 19.7 | 179.0 | **198.7** | 10–50ms ❌ **低估 4–20×** |
| 5,000 | 15 MB | 188.1 | 877.1 | **1,065** | — |
| 10,000 | 30 MB | 463.1 | 1,736.0 | **2,199** | 0.1–0.5s ❌ **低估 4–22×** |
| 50,000 | 150 MB | 1,647.8 | 8,628.7 | **10,277** | — |

**端到端**（从 SQLite 读回 `shot_vectors()` + 排序取 top10），10,000 镜头：**2,112 ms**。

写入成本：10,000 条镜头级向量耗时 **6,694 ms**（0.67 ms/条）—— 入库时的一次性成本，可接受。

**结论修正**：真实可用上限是 **几百个镜头**，不是"上千"。
1,000 镜头已经 200ms，10,000 镜头 2.2 秒 —— 交互式检索 2 秒等待不可接受。

**这个更正的意义**：初版的"等到上千再谈 ANN"过于乐观，会让下一次升级判断偏晚。
现在把触发条件写成 **"镜头数接近 1,000"**。

> **方法论教训**：性能数字必须实测。估算写进验收报告，就是没有证据的结论 ——
> 而本项目的规矩是"验收必须可复现证据"。

## 3. 顺带调研：中文标签检索，要不要用 FTS5？

交付报告记录了"标签检索只是字符串匹配（`LIKE`）"。既然在补调研，
顺便验证 **SQLite 自带的 FTS5 能不能做得更好**（它是 SQLite 的一部分，**public domain，零新增依赖**）。

**实测结果反直觉：`LIKE` 反而是唯一全对的。**

| 查询 | 字数 | `LIKE` | FTS5 `unicode61` | FTS5 `trigram` |
|---|---|---|---|---|
| 云 | 1 | ✅ 1 | ❌ 0 | ❌ 0 |
| **星云** | 2 | ✅ 1 | ✅ 1 | ❌ 0 |
| **测试** | 2 | ✅ 2 | ❌ 0 | ❌ 0 |
| 抽象艺 | 3 | ✅ 1 | ❌ 0 | ✅ 1 |
| 抽象艺术 | 4 | ✅ 1 | ✅ 1 | ✅ 1 |
| 电视测试 | 4 | ✅ 1 | ❌ 0 | ✅ 1 |
| 俄罗斯方块 | 5 | ✅ 1 | ✅ 1 | ✅ 1 |
| **合计** | | **7/7** | **4/7** | **4/7** |

（SQLite 3.50.4，语料为中文本任务产生的真实标签）

**失效机制**：

- **`unicode61`**：按"词"匹配。中文没有空格，整条标签被当成一个大 token ——
  所以 `星云` 命中（它就是整条标签），而 `测试` **命中 0**（标签是"测试画面"/"电视测试卡"，
  `测试` 不是独立 token）。**中文子串匹配直接失效。**
- **`trigram`**：把文本切成连续 **3 字**片段，查询也必须 ≥3 字 ——
  所以 `星云`（2 字）、`测试`（2 字）**都命中 0**。而中文标签里 **2 字词极常见**。

**结论：不引入 FTS5，`LIKE` 保持现状是对的。** 这是有数据支撑的决定，
不是"没想到"。

> **边界提醒**：这个结论只对"标签是**短词/短语**、查询是**中文子串**"的场景成立。
> 如果将来标签变成整段描述、查询变成自然语言长句，FTS5 的价值需要重新评估。

## 4. 结论与升级触发条件

| 技术选型 | 决定 | 理由 |
|---|---|---|
| 本地存储 | **SQLite（标准库）** | 单文件、事务、索引；符合"插件内建库、不做通用存储抽象" |
| 向量检索 | **全表扫描 + Python 余弦（从零）** | 14 个镜头 2.6ms；引入任何 ANN 都要带二进制，与"插件零依赖"冲突 |
| 标签检索 | **`LIKE`（保持现状）** | 实测 `LIKE` 7/7，FTS5 两种 tokenizer 各只有 4/7 |

**升级触发条件（明确写下来，避免下次判断偏晚）**：

1. **镜头数接近 1,000** → 语义检索延迟将达 ~200ms，需要重新评估
2. 重新评估时的**首选候选是 `sqlite-vec`** —— 它与现有 SQLite 存储同源，
   改动面最小（Apache-2.0，可商用）
3. 评估时**必须实测**，不能再用估算
4. **候选清单里排除 chromadb** —— 它的内置 embedding function 与
   「插件经 Core Capability 调 AI」的原则冲突

**现在不做**的理由：任务书明确禁止"为将来预留的扩展点"，
而当前规模（14 个镜头）用不上。**触发条件是"接近 1,000"，不是"现在"**。

## 5. 本次调研的局限（如实说明）

1. **没有实测这 6 个 ANN/向量库的实际性能** —— 只核了许可证、维护状态与架构适配性。
   真要选型，必须在实测后决定（装这些库本身就要引入依赖，超出了本次"补调研"的范围）。
2. **没有实际安装任何候选库** —— 因此"架构冲突"的判断基于其分发形态
   （C/C++ 扩展、需加载 `.dll`、包体积），不是基于集成尝试。
3. **FTS5 的结论基于 10 条中文标签的小语料** —— 足以说明 tokenizer 的失效机制，
   但不构成规模化的基准测试。
4. **没有调研"用 SQLite 存向量以外"的方案**（如独立列存、二进制文件 + mmap）。
   当前 SQLite 完全够用，不需要展开。
