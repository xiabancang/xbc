## 0. 先给结论（三个核心问题的直接回答）

### Q1：Caption-then-Embed vs Joint Embedding，视频检索场景怎么选？

**不是二选一，而是"主力 + 补充"。** 实测数据（同一批 14 帧、同样 10 个中文查询）：

| | 中文 CLIP（联合嵌入） | Caption 路线（现有） |
|---|---|---|
| top-1 命中 | **6/10** | 2/10 |
| 正确项进前 3 | **8/10** | 3/10 |
| 逐条对比 | **8 胜 1 平 1 负** | 1 胜（`宇宙星云`：排名 1 vs CLIP 的 4） |

逐条看**两者是互补的**，不是替代关系：

| 查询 | CLIP 最好排名 | Caption 最好排名 | 谁赢 |
|---|---|---|---|
| 夜景 | **1** | 13 | CLIP 大胜 |
| 电子游戏画面 | **1** | 4 | CLIP |
| 像素风格画面 | **1** | 4 | CLIP |
| 分形图案 | **1** | 6 | CLIP |
| 电视信号测试图 | **3** | 8 | CLIP |
| 彩条测试卡 | **5** | 10 | CLIP |
| 抽象的彩色几何图案 | **3** | 4 | CLIP |
| 色彩渐变背景 | **1** | 2 | CLIP |
| 星空 | 1 | 1 | 平 |
| **宇宙星云** | 4 | **1** | **Caption** |

**为什么 Caption 会在"宇宙星云"上赢**：Caption 路线嵌入的是 AI 写出的**中文描述**，
VLM 看到 life 细胞自动机画面时写的正是"夜空/星云/宇宙"——**描述里直接有那个词**。
而中文 CLIP 的图-文对齐是在通用图文对上训出来的，对这种**非自然图像**（合成图案）没有先验。

**结论**：
- **合成/图形/测试图类素材** → 联合嵌入明显更强（CLIP 8 胜里 6 胜属于这类）
- **自然场景 + 抽象概念** → Caption 路线仍有一席之地
- **正确做法**：CLIP 做主力召回，Caption 的向量作为第二路，分数融合

### Q2：在"纯本地 + Python 单目录插件 + 无编译产物 + 中文支持"约束下，有哪些可行的 Joint Embedding 方案？

**只有一个真正可行：中文 CLIP 系（CN-CLIP）**。理由不是"它最好"，而是**其他候选在中文上直接不可用**：

| 方案 | 中文实测 | 判定 |
|---|---|---|
| **中文 CLIP `chinese-clip-vit-base-patch16`** | **top-1 6/10** | ✅ **唯一可用** |
| MobileCLIP2-S0（amon-hen 用） | 中文 **1/10** vs 英文 **5/5** | ❌ 语言不匹配（见 §2 根因实证） |
| 其他英文 CLIP（OpenAI CLIP / SigLIP 等） | 同 MobileCLIP2（英文词表） | ❌ 同类问题 |

**"无编译产物"这个约束的真实情况**（实测）：
- 中文 CLIP 走 `transformers` 需要 **torch**（CPU wheel ~200MB）—— 是二进制 wheel，**不需要本地编译**，但**体积很大**
- 想避开 torch，中文 CLIP 官方**支持导出 ONNX**（`deployment.md`，并提供预训练 TensorRT 模型）→ 用 `onnxruntime`（~15MB）替代 torch。**这条路径我没有实测**，标为待验证

### Q3：有没有 Caption + 图片 embedding 混合检索的成熟先例？

**在调研范围内没有找到"Caption embedding + 图片 embedding 分数融合"的产品级先例。** 找到的是**相邻但不相同**的三类：

| 先例 | 融合的是什么 | 是不是我们要的 |
|---|---|---|
| **amon-hen** `--mode hybrid` | **视觉嵌入（MobileCLIP2）+ 语音转写文本**，按分数合并、`match_type="hybrid"` | 一半（视觉+文本，但文本来自**语音**不是**画面描述**） |
| **arkiv** | 视觉描述 + 转写 → **统一用 bge-m3 文本嵌入**（单路） | 不是（它没有图片嵌入这一路） |
| **MaterialSearch** | 纯中文 CLIP 图片嵌入（单路） | 不是 |
| **学术界的 caption bridging / 重排** | 用 caption 生成结果再用 CLIP 相似度**重排** | 接近，但顺序相反（我们是先 CLIP 再用 caption 补） |

**这是一个真实的空白点**，也是 XBC 的机会：**双路召回（图片嵌入 + 画面描述嵌入）+ 分数融合**，
在已有产品里没人做得很完整。而本报告的实测数据（8 胜 1 平 1 负 + 一处 Caption 明显更优）
说明这个融合**有实测基础，不是空想**。

## 1. 实测：三条路线同数据对比

### 1.1 方法与评测集

- **语料**：TASK-009 的真实素材库，**14 个镜头帧**（8 个 ffmpeg 合成视频）
- **查询**：**10 个中文查询**（TASK-009 只测了 7 个，本次补齐）
- **Ground truth 是客观的**：14 帧来自 7 种 lavfi 源，每种源画面语义明确，
  `查询 → 应当命中的来源` 的映射**事先定好**，不是事后编的

| 来源 | 镜头数 | 对应查询 |
|---|---|---|
| mandelbrot（分形） | 3 | 抽象的彩色几何图案 / 分形图案 |
| smptebars（彩条测试图） | 3 | 电视信号测试图 / 彩条测试卡 |
| life（细胞自动机） | 2 | 星空 / 宇宙星云 / 夜景 |
| gradients（渐变） | 2 | 色彩渐变背景 |
| rgbtestsrc（色块） | 2 | —（干扰项） |
| testsrc2（像素动图） | 1 | 电子游戏画面 / 像素风格画面 |
| testsrc | 1 | —（干扰项） |

### 1.2 结果

| 路线 | 中文 top-1 | 中文 前 3 | 英文 top-1（对照） |
|---|---|---|---|
| **中文 CLIP ViT-B/16** | **6/10** | **8/10** | 未测（中文模型不做英文） |
| **Caption-then-Embed（现有）** | 2/10 | 3/10 | — |
| **MobileCLIP2-S0（amon-hen）** | **1/10** | 3/10 | **5/5** |

> Caption 路线的 2/10 是**本次实测**（用插件自己的 `library_search_semantic` 工具跑，
> 与 TASK-009 完全同路径）。TASK-009 报告里写的"4/7"是在**另一次库重建**的数据上得到的，
> 两者差异的来源见 §1.4。

### 1.3 中文 CLIP 的性能实测

```
模型        OFA-Sys/chinese-clip-vit-base-patch16（188.3M 参数，512 维输出）
设备        CPU（18 线程），torch 2.14.1+cpu
加载        24.3s（首次下载后；纯加载 0.4s）
图像编码    116 ms/帧（14 帧 1.63s，串行）
文本+检索   37 ms/查询（含全量排序）
```

### 1.4 一个必须记录的发现：Caption 路线的结果**不可复现**

同一个素材库，两次重建后的检索质量不同：

| | TASK-009 记录 | 本次实测 |
|---|---|---|
| 同批 7 个查询的 top-1 | 3/7（报告写 4/7，偏宽松） | 2/7 |

原因有二，都已定位：

1. **标签会漂移**：同一帧 `v04_fractal_test#1` 三次入库给出了**三套不同的标签**：
   - `['视频游戏','像素艺术','俄罗斯方块','游戏画面','彩色方块','游戏场景','像素风格']`
   - `['像素游戏','动作冒险','视频游戏','像素风格','冒险','游戏','像素艺术']`
   - 向量随后者变化，检索排名随之变化

2. **嵌入文本与库内可见信息不一致（设计缺陷）**：
   `plugin.py` 里向量是这样算的 ——
   ```python
   text_for_embedding = " ".join([annotated.answer, *annotated.labels]).strip()
   embedded = self.ctx.ai.embedding([text_for_embedding])
   ```
   即向量 = **AI 的整段自由回答 + 标签**。但库里**只存了 `labels`，没存 `answer`**。
   结果是：**你能看到标签，却看不到真正被嵌入的文本**，检索行为无法从库里审计。
   而 `answer` 是一段较长的通用描述，会稀释标签的区分度 —— 这正是
   `testsrc2`（标签为"像素游戏/动作冒险/视频游戏"）能在"色彩渐变背景"上排到前面的直接原因。

**这一条本身就是 TASK-010 要修的东西**，比换模型更紧急。

## 2. MobileCLIP2 中文失效的根因（tokenizer 实证）

amon-hen 的视觉编码器是 **MobileCLIP2-S0**（apple-aiml-research/ml-mobileclip 官方 ONNX 版）。
它在英文上表现正常（**5/5 全对**），中文却只有 1/10。**根因不是模型弱，而是语言不匹配**：

```
'star'          → ['<|startoftext|>', 'star</w>', '<|endoftext|>', PAD…]
'a starry night sky' → ['<|startoftext|>', 'a</w>', 'starry</w>', 'night</w>', 'sky</w>', …]
'星'            → UTF-8 e6 98 9f → ['æĺ', 'Ł</w>']        ← 字节碎片
'空'            → UTF-8 e7 a9 ba → ['ç', '©', 'º</w>']     ← 字节碎片
'抽象的彩色几何图案'   → ['æ','Ĭ','½','è','±','¡','ç','ļ','Ħ', …]   25 个字节碎片 token
```

**机制**：MobileCLIP2 的 BPE 词表是英文的（训练数据 DataCompDR / DFNDR 都是英文网络数据），
**表里没有汉字**，于是中文被拆成 UTF-8 字节、再逐个映射到拉丁字符的 byte-token。
10 个中文查询确实产生 **10 种不同的 token 序列**（不是全同），但它们**都是无语义的字节碎片**，
所以文本塔编出来的向量与图片塔对不上。

**这不是 amon-hen 的 bug** —— 它从未声称支持中文（README 与模型卡都只有英文）。
**但它是"方向 B 不可直接采用"的决定性证据。**

## 4. 逐项目说明

### 中文 CLIP

- **代码仓库**：`OFA-Sys/Chinese-CLIP`（**MIT**，6,013★，最后提交 2026-03-31）
- **论文**：arXiv:2211.01335；训练数据 ~2 亿中文图文对
- **权重许可证**：⚠️ `vit-base-patch16` / `vit-large-patch14` / `vit-huge-patch14` **均未声明**；
  只有 `rn50` 是 Apache-2.0
- **官方 benchmark（零样本 文→图 R@1）**：

  | 模型 | MUGE | Flickr30K-CN | COCO-CN |
  |---|---|---|---|
  | **CN-CLIP** | **63.0** | **71.2** | **69.2** |
  | R2D2 | 49.5 | 60.9 | 56.4 |
  | Taiyi | — | 60.8 | 60.0 |
  | Wukong | 42.7 | 51.7 | 53.4 |

  （R@5 / R@10 见官方 README；CN-CLIP 在三套中文 benchmark 上**全面领先**）
- **已集成到 `transformers`**（`ChineseCLIPModel`），**无需装 `cn_clip` 包**
- **冲突**：torch 依赖体积大；但官方支持导出 **ONNX / TensorRT**（`deployment.md`）
- **本机实测**：top-1 **6/10**、前 3 **8/10**、116 ms/帧、37 ms/查询

### AltCLIP

- **仓库/权重**：`BAAI/AltCLIP`，权重许可证 **`creativeml-openrail-m`**
- **判定**：⚠️ OpenRAIL 系列带**行为能力限制条款**（use-based restrictions），
  不是标准 OSI 开源许可。**夏半仓不做它**，也不用进一步评估性能。
- 理由与台账里 `ollama-python` / `chromadb` 同一原则：**许可不清楚就不碰**

### Taiyi-CLIP

- **仓库/权重**：`IDEA-CCNL/Taiyi-CLIP-Roberta-102M-Chinese`，**Apache-2.0** ✅
- **官方 benchmark**：Flickr30K-CN 零样本 R@1 = **60.8**（CN-CLIP 71.2）、COCO-CN R@1 = **60.0**（CN-CLIP 69.2）
- **判定**：许可最干净，但**中文检索质量低于 CN-CLIP 约 10 个点**。
  作为"许可风险对冲"的备选记录在此，**本次不采用**

### amon-hen

- **仓库**：`flxhrdyn/amon-hen`；PyPI `amon-hen` 0.1.21（2026-09-02）；**MIT** ✅
- **架构（已读源码）**：ONNX Runtime `CPUExecutionProvider`；视觉 `vision_model.onnx`，
  文本 `text_model_quantized.onnx` + `tokenizer.json`；**SQLite + sqlite-vec + FTS5** 单文件索引
- **模型体积（实测查询 HF）**：vision 43.45 MB + text(quantized) 61.35 MB + tokenizer 2.12 MB
  ≈ **107 MB**（README 称"~105 MB RAM"）
- **依赖（实测 `pip install` 结果）**：37 个包，含 **`onnxruntime` 1.30.0** 与
  **`sqlite_vec-0.1.9-py3-none-win_amd64.whl`** —— **两个平台相关的编译二进制**
- **⚠️ 对"无编译产物"的如实修正**：amon-hen **不需要本地编译**（都是预编译 wheel），
  但它**确实带了平台相关的二进制**（Windows 是 win_amd64 专用 wheel）。
  如果夏半仓的约束是"不需要编译器"，它满足；如果是"纯 Python 无二进制"，它**不满足**。

**代码质量观察（值得参考的做法）**：它的 docstring 记录了**实测踩坑**，不是猜测：
> "INT8 量化 Conv 层导致输出几乎完全损坏（与 FP32 的余弦相似度接近零），
> 只量化 8 个 MatMul 层则精度无损但模型几乎没变小"
> "直接用方形 resize 会压扁宽高比，使嵌入偏移约 0.03 余弦 —— 与'好匹配'和'一般匹配'的差距同数量级"

**融合设计（Q3 的先例）**：`pipeline.py` 的 `mode="hybrid"` 同时跑视觉与语音两路，
按分数合并、标 `match_type="hybrid"`。**这是"多路召回融合"的真实产品级先例**，
虽然它融合的是"视觉 + 语音"而非"视觉 + 画面描述"。

### MaterialSearch

- **原仓库**：`myqv/MaterialSearch`（Gitee，凡争）；GitHub 备份 `kun2001github/MaterialSearch-backups`
- **许可证**：**GPL-3.0** ❌ **不可采用**（采用即传染，与商业产品冲突）
- **使用方式**：**参考** —— 只读其设计；它是"纯中文 CLIP 联合嵌入"路线的完整范例
- **默认模型**：`OFA-Sys/chinese-clip-vit-base-patch16`（← 就是那个**权重许可未声明**的模型）
- **官方性能（其 README 自测，J3455 CPU）**：
  - 匹配阈值 0：**≈18,000 图片匹配/秒** 或 **≈5,200 视频帧匹配/秒**
  - 匹配阈值 10：**≈30,000 图片匹配/秒** 或 **≈6,100 帧匹配/秒**
  - 硬件要求：内存最低 2G、推荐 4G；官方测试机 J3455/8G 与 全志H6/2G
- **可借鉴的设计**：SQLite 单库 + 图文特征分表 + "匹配阈值"作为速度/召回的显式权衡旋钮

### arkiv

- **仓库**：`vulture-s/arkiv`（76★，2026-10-04 活跃）
- **许可证**：**PolyForm Perimeter 1.0.1**（GitHub 归类 `NOASSERTION`）
  - 文本明确：**免费用于任何目的（含商业）**，但**不允许"把它做成与 arkiv 竞争的产品"**
    —— 包括"用它的功能重新实现一个替代品，免费也不行"
- **判定**：⚠️ **对夏半仓有实质风险**。夏半仓的素材库插件如果功能上成为 arkiv 的替代品，
  可能落入"竞争产品"条款。**只参考设计，不采用任何代码**。
- **技术栈**：FastAPI + Tauri + SQLite + **ChromaDB** + Ollama（bge-m3 嵌入 / qwen2.5vl:7b 视觉 /
  qwen2.5:14b 对话）+ Whisper large-v3-turbo + Silero VAD + DaVinci Resolve 插件
- **它是 Caption 路线**：视觉描述 + 转写 → 统一 bge-m3 文本嵌入（**没有图片嵌入这一路**）
- **明确支持中文**（CJK-first，中文/日文/英文查询）
- **引用其官方实测数据**（对方向 D 直接有用）：
  - `qwen2.5vl:7b` ≈ **8 秒/帧** vs `qwen3-vl:8b` ≈ **60 秒/帧**（Ollama 下，**约 10 倍差距**）
  - 规模验证：单张 RTX 4070 上完整索引 **1,506 个剪辑**（其中 1,161 个无对白 B-roll）
- **架构冲突（明确，未强行整合）**：它需要 Ollama + ChromaDB + Whisper + torch，
  是"一个完整应用"而非"一个插件"；且它的**核心价值在 DaVinci Resolve 集成与 DIT 工作流**，
  与夏半仓"插件平台"定位不同层面。

## 6. 可落地的候选方案（4 个）

### 候选 A：中文 CLIP 联合嵌入，替换现有语义检索

- **做法**：插件内加载 `chinese-clip-vit-base-patch16`，对关键帧编码 512 维向量；
  查询文本用同一模型编码；余弦检索（沿用 TASK-009 的 SQLite 存储与全表扫描）
- **实测收益**：中文 top-1 从 2/10 → **6/10**；前 3 从 3/10 → **8/10**；编码 116 ms/帧
- **成本**：新增 `torch` + `transformers` + `pillow`；模型 ~600MB 磁盘
- **风险**：**权重许可证未声明** → 建议改用 `chinese-clip-rn50`（Apache-2.0，77M）
  或先向 OFA-Sys 澄清
- **架构合规**：模型在**插件内**加载，不经 Core；仍满足"插件不直接调模型 API"的原始意图
  （这里调的是本地权重，不是云 API）。**但需明确：这会在插件里引入二进制依赖，
  与"插件尽量零依赖"的既有约定冲突，需要你裁决**

### 候选 B：修好现有 Caption 路线（零新依赖，最紧急）

- **B1. 把真正被嵌入的文本存进库**：现在向量由 `answer + labels` 算出，但库里只存 `labels`
  → 检索行为不可审计。把 `answer` 一并入库（或改成只嵌入 `labels`）
- **B2. 去掉 `answer` 的稀释，或给它降权**：长通用描述压过了标签的区分度
- **B3. 优化 VLM prompt**：现有提问是"这个画面的主要内容是什么？属于什么场景或拍摄类型？"
  → 改成要求**检索导向**的描述（具体名词、场景、动作、光线、构图），并约束长度
- **实测依据**：Caption 在"宇宙星云"上打赢 CLIP（排名 1 vs 4），说明**这条路有不可替代的价值**
- **成本**：零新增依赖，只改插件

### 候选 C：双路召回 + 融合（**推荐**）

- **做法**：CLIP 图片向量（候选 A）+ Caption 文本向量（候选 B）**两路都算、分数融合**
  - 融合方式建议 RRF（Reciprocal Rank Fusion，对分数尺度不敏感，不需要调参）
  - 或加权分数融合（需要调权，实测数据可以支撑）
- **实测依据**：CLIP 8 胜 1 平 1 负，**且那 1 负是 Caption 大幅领先**（1 vs 4）
  → 融合的收益空间是**存在的、可量化的**
- **先例**：amon-hen 的 `--mode hybrid`（视觉+语音多路融合、`match_type="hybrid"`）
  证明了"多路召回按分数合并"在产品里可行
- **成本**：CLIP 编码 116 ms/帧（一次性）+ Caption 已有成本；存储 +3KB/镜头
- **这个方案直接回答 Q3**：调研范围内**没有产品做过"图片嵌入 + 画面描述嵌入"的融合**，
  XBC 做这个是有差异化价值的

### 候选 D：ONNX 化的中文 CLIP（省掉 torch）

- **做法**：用官方 `deployment.md` 的导出脚本把中文 CLIP 转 ONNX，运行时只用 `onnxruntime`
- **依据**：官方 README 明确写了 ONNX/TensorRT 支持并提供预训练 TensorRT 模型；
  amon-hen 也证明了"ONNX Runtime + 纯 CPU"这条路在本机可行（26 ms/帧）
- **收益**：免除 ~200MB 的 torch 依赖，与 amon-hen 的依赖形态看齐
- **⚠️ 未实测** —— 我只读了官方文档，**没有实际导出并跑通**。落地前必须先做一次验证

## 7. 本次调研的局限（如实说明）

1. **评测集是 14 个合成画面的镜头，不是真实世界素材**。这 14 帧语义区分度很高
   （分形/彩条/细胞自动机/渐变/色块/像素图），**不能代表实拍素材**。
   三者的排名在真实素材上可能不同。
2. **MobileCLIP2 的英文 5/5 是在同一批合成画面上得到的**，样本仅 5 个查询。
   它的**中文 1/10 这个结论是稳的**（tokenizer 机制已实证），但英文具体分数不必外推。
3. **没有做超参调优**：中文 CLIP 用的是默认 prompt（无"a photo of"之类模板）。
   CLIP 系模型对 prompt 模板敏感，加模板可能提升，**未测**。
4. **候选 D 未实测**（见上）。
5. **`chinese-clip-vit-base-patch16` 的权重许可证未声明** —— 我只查到"未声明"这个事实，
   **无法替官方下"可以商用"的结论**。
6. **`VideoChain` 未能核实**，如实标注而非编造。
7. **没有实测 arkiv / MaterialSearch / VideoSeek 本身** —— 只核了许可证、依赖形态与官方数据。
   它们的体量（完整应用 + Docker + GPU 栈）不适合在本次调研里跑。
