## 核心线索 1：分拍（beat）先于剪辑，且每拍标「谁主导这一拍」

它的产物链是：

```
recap_story_plan.json    故事计划：观众承诺 / POV / 戏剧问题 / 每拍"发生了什么变化"
        ↓
clip_plan.json           每拍 → 一条带理由的选段（source_id + source_start/end）
        ↓
visual_audio_board.json  每拍的画面任务 + **声音归属（audio_owner）** + 旁白任务
        ↓
narration.json           只包含"确实需要旁白"的块（其余留白给原声）
        ↓
timeline.json            多轨时间线（原声 / 旁白 / BGM / 字幕 / 叠层）
```

**关键字段**（原文节选，来自其 README 的示例文件）：

```json
{
  "beat_id": "b03",
  "source_id": "episode-03",
  "source_start": 1292.0,
  "source_end": 1305.24,
  "output_start": 9.206666,
  "output_end": 22.446666,
  "picture_job": "performance",
  "preferred_moment": "完整原声「我日日夜夜地想你…挫骨扬灰」",
  "audio_owner": "original_dialogue",
  "narration_job": "none",
  "handoff": "旁白先补关系，原声/动作发生时完全让位；下一拍承接人物反应。",
  "playback_speed": 1.0
}
```

### 对我们有参考价值的三点

1. **`audio_owner`** —— 每一拍显式声明"谁主导声音"（原声对白 / 旁白 / 动作声 / 沉默）。
   **不是"有对白就压旁白"，而是先决定归属再写词。**
2. **`narration_job: "none"`** —— 旁白**可以什么都不做**。它的示例里全片只有 7 个旁白块，
   有一段连续 13 秒完全留给原声。我们做配音时容易默认"每一拍都要有旁白"，这个设计反对那个默认。
3. **`handoff`** —— 明确写出"这一拍怎么交给下一拍"。音画同步最容易出问题的地方
   就是交界处（旁白什么时候进、什么时候出），它把这件事写成字段而不是靠渲染时猜。

## 核心线索 2：先剪后配，时间轴天然对齐

> 原文："剪辑模式先把长视频剪成成片，再对着成片写解说"

**先剪后配**意味着**旁白的时间轴就是成片的时间轴**，不用在做完后去"对齐原片"。
反过来（先按原片写词再剪）才会产生"配完发现画面被剪掉了"的问题。

对我们：TASK-011 已经产出"每段文案 → 选中的镜头"，**这本身就是一份剪点计划**。
如果 TASK-013 要做成片，时间轴应当由**选中的镜头拼出来的成片**决定，
而不是由原片时间码决定。

## 核心线索 3：质量门是机器可读的文件，不是"我看了一眼"

它每步都留可核对的产物：旁白 lint、组装 QC、交付 QC、看片修改日志。
交付 QC 里是 VMAF / SSIM / PSNR、响度、逐段旁白完整性、`verdict` / `blocking_codes`。

对我们的价值：**与既有的"验收必须是可复现证据"一致** ——
音画同步的验收不该是"听起来还行"，而应该有可测量的指标（响度、旁白是否完整、是否有截断）。
具体用哪些指标，**等任务书**。
