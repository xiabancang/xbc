## 1. 实现了什么（对照任务书逐条）

| 任务书 | 实现 |
|---|---|
| 1. 修 TASK-008 报告里"确定要改"的两处 | `types.py` 声明 `labels` 语义；`vision_prompt()` 按**图片张数**出措辞 |
| 2. 素材库（插件内） | `plugins/video_analyzer/xbc_va_library.py`（SQLite，5 张表） |
| 3. 扫描与增量分析 | `library_scan` / `library_retry` / `library_rebuild`：内容哈希判定、单文件失败隔离 |
| 4. 检索 | `library_search_labels`（精确/模糊）、`library_search_semantic`（embedding） |
| 5. 导出 | `library_export`：H.264/MP4 + faststart，输出侧精确定位 |
| 6. 失败与重建 | 失败留在库里可重试；库可整体丢弃重建；中断后 `pending` 可续 |

**存储选型**：SQLite（标准库 `sqlite3`）。单文件、有事务与索引、库损坏可整体丢弃重建。
**不做通用存储抽象** —— 任务书禁止项，且只有一个业务插件时抽象层是纯负担。

**表结构**：

| 表 | 关键字段 |
|---|---|
| `videos` | `path`、**`file_hash`（内容哈希）**、`size_bytes`、时长、分辨率、`status`、`error`、`analyzed_at` |
| `shots` | `video_id`、`shot_index`、起止秒、`ai_provider` / `ai_model` |
| `frames` | `shot_id`、时间码、图片路径 |
| `labels` | `shot_id`、标签文本、`source` |
| `vectors` | `shot_id`、`frame_id`（0 = 镜头级）、provider/model/dim、float32 BLOB |

**增量判定只看内容哈希**，不看路径、不看修改时间 —— 改名/复制/时间戳被同步工具改动都不该触发重分析，
内容真的变了才重分析。

**新增 7 个工具**（插件共 12 个）：
`library_scan` / `library_retry` / `library_rebuild` / `library_status` /
`library_search_labels` / `library_search_semantic` / `library_export`。

### 验收 1 —— 两处接口问题

**(a) `labels` 语义已声明**（模块文档 + 两个结果类的类注释）：

```
types.py 含「自由文本」: True
types.py 含「不保证可枚举」: True
types.py 含「不保证归一」: True
VisionResult 类注释含「不保证可枚举」: True
VisionAnswer 类注释含「不保证可枚举」: True
```

声明内容：`labels` 是模型生成的自由文本，不保证可枚举、不保证归一、不做去重语义判断；
**要拿它做筛选/聚合/建索引，归一化是调用方自己的事**。

这个声明有**实测支撑**：同素材两次入库，标签总数从 88 变成 90 —— 标签确实不可枚举。

**(b) 提示词与 `images` 列表自洽**：

```
图片 1 张 → 含「这张图片」: True；残留单数措辞: False
图片 3 张 → 含「3 张图片」: True；残留单数措辞: False
图片 5 张 → 含「5 张图片」: True；残留单数措辞: False
提问模式 4 张 → 含「4 张图片」: True；问题原文保留: True
```

多张时的语义被定死：**同一场景的不同视角或时刻，综合成一次判断**。
单张措辞与 TASK-008 逐字相同。

### 验收 3 —— 增量与容错

**增量**（新增 1 个视频后扫描）：`found=7  analyzed=1  skipped=6 failed=0`，
被分析的正是新文件，其余 6 个按哈希跳过。

**容错**（把一个文本文件命名为 `.mp4`）：

```
found=8  analyzed=0  skipped=7  failed=1
  ✗ v08_broken.mp4: 无法读取视频时长（文件可能损坏或不是有效视频）：…
库状态: 视频 8  镜头 13  标签 81  向量 26
未成功的记录: [('v08_broken.mp4', 'failed')]     ← 失败项留在库里
```

**重试**：

```
重试（文件仍是坏的）: candidates=1  analyzed=0  failed=1  missing=0
                      ✗ 仍失败 v08_broken.mp4: 无法读取视频时长…
把文件换成真视频后重试: candidates=1  analyzed=1  failed=0
                      ✓ 重试成功 v08_broken.mp4  镜头 1
```

单个视频失败**没有阻塞**其余 7 个的入库；失败项**留在库里**所以能被重试找到。
（早期实现只对"已存在的记录"置失败，导致连探信息都失败的坏文件直接消失在库里 ——
用户看到 `failed=1` 却找不到是哪一条。已修。）

**分析中断可续**：入库前状态先置为 `pending`，成功才置 `ok`。中途被打断留下的是
`pending`，`library_retry` 把它当未完成项接着跑，不需要重扫全量。

## 3. 真实素材的入库记录（规模、耗时）

| 阶段 | 规模 | 耗时 |
|---|---|---|
| 首次入库（8 个视频 / 14 个镜头） | 1,433,709 字节 | **65.1s** |
| 模型常驻后重建同一批 | 同上 | **11.6s** |
| 重复扫描（无变更） | 8 个视频全部跳过 | **0.0s** |
| 单视频增量入库 | 1 个视频 / 1 个镜头 | 约 1.5s |

入库产物：**14 个镜头 / 14 个关键帧 / 88 个标签（去重 43）/ 28 个向量（14 帧级 + 14 镜头级，768 维）**。

**耗时构成**：每个镜头 = 1 次视觉理解（`qwen2.5vl:3b`）+ 1 次向量化（`nomic-embed-text`）。
65.1s ÷ 14 ≈ 4.6s/镜头，其中绝大多数是视觉模型推理（首次含冷加载）。

**素材说明（必须交代）**：本机没有实拍素材。素材由 ffmpeg 的 lavfi 源合成 ——
它们是**真实的 MP4 文件**（真实编码、真实解码、真实抽帧、真实 AI 分析），
但画面不是摄像机拍的。8 个视频各由两段视觉语义差异明显的素材拼成，因此各 2 个镜头：

| 素材 | 两段内容 |
|---|---|
| v01_abstract_bars | mandelbrot 分形 + smptebars 彩条 |
| v02_cells_gradient | life 细胞自动机 + gradients 渐变 |
| v03_bars_rgb | smptebars 彩条 + rgbtestsrc 色块 |
| v04_fractal_test | mandelbrot 分形 + testsrc2 动图 |
| v05_cells_test | life 细胞自动机 + testsrc |
| v06_gradient_rgb | gradients 渐变 + rgbtestsrc 色块 |
| v07_new_mandel | mandelbrot 分形（增量测试用） |
| v08_broken | 先是文本文件（失败测试用），后换成真视频 |

**这些素材不能代表真实世界画面**，下面所有检索质量结论仅对本批素材成立。

## 7. 过程中发现的问题与处理

### 7.1 修掉的真缺陷（5 个）

| # | 缺陷 | 影响 | 修复 |
|---|---|---|---|
| B10 | `sqlite3.Connection` 的 `with` **只管理事务、不关闭连接** | 库文件一直被锁 → `library_rebuild` 直接 `WinError 32 另一个程序正在使用此文件`；同时是句柄泄漏 | 新增 `Library.session()` 上下文管理器，负责关闭连接 |
| B11 | 库文件损坏时 `library_rebuild` 也起不来 | `initialize()` 先打开损坏文件就 `file is not a database` → **重建永远救不回来**（而这是验收 6 的要求） | `library_rebuild` 先删文件、不依赖打开成功；`initialize()` 把 sqlite3 异常翻译成可操作的 `LibraryError` |
| B12 | 在 `upsert_video` **之前**就失败的视频不写库 | 用户看到 `failed=1` 却在库里找不到这条 → 无法重试 | 失败分支在记录不存在时也 `upsert_video` 一条 `failed` 记录 |
| B13 | 标签检索一个镜头命中多个标签时**重复出现** | 调用方要的是镜头列表，拿到的是"镜头×标签"列表 | 查询改为按 `shot_id` 分组，命中标签合并进 `matched_labels` |
| B14 | 代码注册 12 个工具，**清单只声明 5 个** | 违反"零成本清单"契约（不加载代码就该知道插件提供什么）；已有测试守着 | 补齐 `plugin.json` 的 `tools`，版本升到 0.3.0 |

B12–B14 都是**真实使用时才暴露的**：B12 是制造坏文件时发现的，B13 是看检索输出时发现的，
B14 是全量测试发现的。

| 模型常驻后重建 | **11.6s**（≈0.8s/镜头） |
| 重复扫描（无变更） | **0.0s**，8 个视频全部按哈希跳过，**零次模型调用** |
| 单视频增量 | 约 1.5s |

**耗时几乎全在视觉模型推理上**。向量化（`nomic-embed-text`）在 14 条短文本上是秒级以内。
按 4.6s/镜头估算，**1 小时的素材（假设切出 300 个镜头）首次入库约 23 分钟**；
模型常驻后约 4 分钟。这个量级对"每周新增素材"的节奏是可接受的，**但必须后台跑**
——当前实现是同步的，一次 `library_scan` 会占住调用方直到扫完。

### 8.2 哪些搜得到、哪些搜不到

**标签检索搜得到的**：标签里**字面出现**的词。实测 "抽象艺术" → 5 个镜头、
"几何图形" → 3 个镜头、"测试画面" → 5 个镜头。

**标签检索搜不到的**（且这不是 bug，是设计）：查询词与标签不是同一个词就找不到。

| 查询 | 标签里实际有的词 | 标签检索 | 语义检索 |
|---|---|---|---|
| 星空 | 夜空、星云、宇宙 | **0** | top-1 命中（0.8187） |
| 宇宙星云 | 夜空、星云、宇宙（离散） | **0** | top-1 命中（0.8698） |

**这就是任务书要求"必须同时支持两种检索"的实证**：标签是自由文本、不保证归一，
纯标签匹配会漏掉所有"同义但不同字"的情况。反过来，标签检索的**精确性**是语义检索给不了的
——要"所有带这个词的镜头"，语义检索做不到精确。

### 8.3 语义检索准不准

**4/7 组 top-1 正确，3/7 不正确。** 逐条见 4.2。不准的三条，根因各不相同：

**（1）`电子游戏画面` —— 描述过于泛化，泛化描述与任何查询都有中等相似度**

`v03_bars_rgb 镜头1`（rgbtestsrc 色块）被 AI 描述成 **"测试 / 测试画面 / 测试图像"** ——
三个词全是泛化词。这类描述与任何查询的相似度都在 0.8 上下，于是它把
"电子游戏画面"的 top-1 占了（0.8276），而**真正被描述成"视频游戏/像素艺术"的那个镜头排在第 5 名以外**。

**（2）`电视信号测试图` —— 同类问题，只是没那么极端**

分形镜头（描述"几何图形/抽象艺术/色彩斑斓"）拿到 0.6456，正确的测试图镜头 0.6116。
差 0.034，正确项掉到第 3 位。

**（3）`夜景` —— 中文短语的语义距离不符合直觉**

含"夜空/星云/宇宙"的镜头得 0.5954，分形镜头得 0.6526。也就是说
`nomic-embed-text` 认为"夜景"更接近"几何图形/抽象艺术/色彩斑斓"而不是"夜空/星云"。
这不是实现问题，是**向量模型在这个词上的判断与人的直觉不一致**。

**一个必须说清的语义（决定了检索质量的上限）**：

库里存的向量是 **AI 生成描述文本的 embedding，不是图片 embedding**。所以
**检索质量的上限 = 描述质量的上限**。
- 好处：不需要多模态向量模型，`ctx.ai.embedding` 就够了
- 代价：**描述里没有的概念，语义检索也找不回来**。上面三条不准的查询，全部可以追溯到
  "AI 对那个画面的描述里根本没有那个概念"

**同一个素材两次入库，标签会变**：`v04_fractal_test 镜头1` 一次被描述成
"视频游戏/像素艺术/俄罗斯方块"，另一次是"像素游戏/动作冒险/视频游戏"。
**库的内容会随入库时间漂移**，同一批素材重建两次的标签总数是 88 和 90。

### 8.4 库的规模上限（当前实现的能力边界）

语义检索是**全表扫描 + Python 逐条算余弦**，没有 ANN 索引、没有向量缓存：

| 镜头数 | 向量体积（768 维 float32） | 单次查询估算 |
|---|---|---|
| 14（本次实测） | 14 × 3KB ≈ 42KB | 无感 |
| 1,000 | ≈ 3MB | 约 10–50ms |
| 10,000 | ≈ 30MB | 约 0.1–0.5s |

**这是刻意的**：任务书禁止"为将来预留"，而当前规模（几十个镜头）完全不需要索引。
等到镜头数上千再谈 ANN 才是对的时间点。

### 8.5 与 TASK-008 接口反馈的呼应

TASK-008 报告里"**确定要改**"的两条已修（`labels` 语义、提示词与列表自洽），
"**待定**"的第三条（结构化 `answer`）在本任务中**没有触发**：
素材库只要自由文本描述就够用，不需要布尔/枚举答案。

**本次新增的一条接口压力**（记录，不自行扩大范围）：
语义检索的质量被描述质量卡住，而**描述质量是能力层的固定提示词决定的**。
插件无法影响"AI 怎么描述这个画面"。如果将来要提高检索质量，可选的路径是
（a）在插件里自己组织更好的提示词（需要能力层支持自定义描述要求），或
（b）改 `qwen2.5vl:3b` 这个模型。**两条都不在本任务范围内**，只记录。
