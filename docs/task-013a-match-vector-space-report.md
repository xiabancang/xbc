## 1. 逐项回答

### 1.1 文案匹配调用哪个向量空间？

**`chinese_clip / chinese-clip-rn50`，1024 维，模态 `image`。**

**证据 A —— 匹配结果文件自己记录了空间。**
TASK-011 起，结果 JSON 的 `space` 字段就是落盘的：

```
文件：…\夏半仓工具箱\data\video_analyzer\matches\默认.json
创建：2026-10-05T11:03:36
space = provider='chinese_clip'  model='chinese-clip-rn50'  dim=1024  modality='image'
```

**证据 B —— 现场实测（刚才跑的）。** 同一段文本分别走两个工具：

| 工具 | 返回的空间 | top-1 分数 |
|---|---|---|
| `library_search_semantic` | `chinese_clip/chinese-clip-rn50` **1024 维** | **0.551** |
| `script_match` | `chinese_clip/chinese-clip-rn50` **1024 维** | **0.551** |

**两者一字不差。** 如果是两个空间，分数不可能相同。

### 1.2 用的是什么编码器？

**中文 CLIP 的文本塔**（同一个模型的文本编码器）。

原因写在代码注释里（TASK-010 的结论）：查询文本**必须由该空间自己的 Provider 编码**，
才能与库里的图片向量落在同一个向量空间。
`_score_query()` 里就是 `context["owner"].embedding(...)`，而 `owner` 由 `_retrieval_context()`
按**选中空间**解析出来 —— 两个工具共用这一个函数。

**不是 ollama。** 库里的 ollama 768 维向量是另一个空间，任何一次匹配都不碰它。

### 1.3 为什么和素材库检索不是同一个空间？

**它们就是同一个空间 —— 这个前提不成立。**

两个工具的取数路径是**同一份代码**：

```
script_match            ─┐
                        ├─→ _retrieval_context(space="auto")  ← 选空间 + 取镜头向量 + 解析 Provider
library_search_semantic ─┘            └→ _score_query(...)    ← 编码查询 + 余弦排序
```

- 两者的 `space` 默认值都是 **`"auto"`**（`script_match` 的签名默认值；UI 也不覆盖它）
- `_pick_space(spaces, "auto")` 的逻辑是**优先图片模态**：
  ```python
  # auto：优先图片向量（实测质量更高），没有就退回任意一个
  return next((s for s in spaces if s["modality"] == "image"), None) or spaces[0]
  ```
- 所以只要有图片空间，**两个工具都选它**

TASK-011 还专门有一条测试锁住这件事：
`test_reuses_the_task_010_retrieval_exactly` —— 断言匹配给出的
`(shot_id, score)` 与 `library_search_semantic` **逐字段完全一致**。

## 2. 那 0.5510 和 0.4919 的差异是怎么来的？

**因为查询文本不一样。** 相似度是「文本向量 × 图片向量」算出来的，
文本换一个字，向量就变，分数当然变。

实测（**全部在同一图片空间**）：

| 查询文本 | 分数 |
|---|---|
| 夜晚的城市，灯光闪烁，街道上人来人往。 | **0.551** |
| 夜晚的城市，灯光闪烁，街道上人来人往（无句号） | 0.5484 |
| 夜晚的城市, 灯光闪烁, 街道上人来人往。（半角逗号） | 0.5593 |
| 夜晚的城市 灯光闪烁 街道上人来人往（空格代替逗号） | 0.5663 |
| 城市夜晚，灯光闪烁 | 0.5231 |
| 人来人往的街道 | 0.5283 |
| 夜晚的城市 | 0.5 |
| **夜晚** | **0.4909** |
| 城市 | 0.4729 |

**一眼就能看出规律**：文本越短、信息越少，分数越接近 0.47–0.5 那条线；
越接近原句，越往 0.55 走。

**关于 0.4919 本身 —— 我没能精确复现。** 试了 10 种写法，最接近的是
**`夜晚` → 0.4909（差 0.001）**。所以它极可能来自某个**我不知道的查询文本**
（或某个已不存在的库状态）。**如实说明，不硬凑**。

但差异的**机制**已经证清：同一个空间里，不同文本本来就给不同分数。

## 3. 要求 2：会不会走到文本空间？—— 会，但**不是现在，而且没有提示**

### 3.1 设计如此，不是遗漏

`space="auto"` **优先图片空间**是**故意的**，理由写在代码注释里：
TASK-010 实测图片空间 top-1 **10/10**、文本空间 **2/10**，所以优先前者。

所以「匹配该走哪个空间」这个问题的答案是：**它已经走了对的那个。**

### 3.2 但**静默降级**是真缺口

```python
return next((s for s in spaces if s["modality"] == "image"), None) or spaces[0]
                                                                            ↑
                                                       没有图片空间时，悄悄退回"任意一个"
```

如果库里**没有**图片空间（例如 CLIP 还没装好、或素材还没重新分析），
`space="auto"` 会**默默用文本空间**跑，而那个空间的准确率只有 **2/10**。

**这正是你昨天的处境**：库里只有 ollama 768 维 → 匹配用的就是文本空间。
今天补上 CLIP 之后，它才切到图片空间。

**问题在于：整个过程没有任何提示。**
降级发生时，结果里虽然带 `space` 字段，但**界面不显示**它（见 3.3），
所以用户**只能靠分数猜**—— 你这次就是这么猜的。

### 3.3 界面不显示空间（这才是你产生疑问的根因）

我 grep 了整个匹配页：**`space` / `provider` / `dim` 一个都没有**。

- 工具返回里**有**：`{"provider": "chinese_clip", "model": "chinese-clip-rn50", "dim": 1024, "modality": "image"}`
- UI 里**一个都没渲染** —— 匹配页只显示分段、候选、分数、镜头

所以界面上**看不出**当前用的是哪个空间。**数据在，界面没给看。**

### 3.4 文本空间 2/10 会影响匹配质量吗？

**会影响 —— 但只在降级发生时。**

那个 2/10 是 TASK-010 在 16 张合成图语料上、针对**整库选镜头**测的。
文案匹配复用的是同一条检索路径，所以同一个空间下质量特征一致。

**当前你的库有图片空间 → 不受影响。**
**但如果哪天 CLIP 掉了（模型被删、Python 换回缺包的那个），匹配会悄悄退化，且界面上看不出来。**
